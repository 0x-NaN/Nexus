PROBLEM STATEMENT (THEME 5, VERBATIM CONTEXT)
===================================================================
As autonomous AI agents multiply across financial services, there's no standard safety infrastructure to govern them: no granular permissions, no dynamic spend enforcement, no way to instantly shut down a misbehaving fleet, and no audit trail that would hold up to a regulator. A single compromised or malfunctioning agent could execute unauthorized transactions faster than any human would notice. This infrastructure is the foundation that makes trustworthy agent deployment possible.

===================================================================
PROJECT SUMMARY — WHAT NEXUS IS
===================================================================
Nexus is a real-time governance layer that sits between an autonomous agent and the transaction it's trying to execute. Every transaction request is evaluated against policy before being allowed through. A human operator can instantly halt every agent in the fleet with a single kill switch. Every decision — allowed, denied, or flagged — is permanently logged with a stated reason and can be exported as CSV.

===================================================================
CORE FEATURES (use as main content slides, one concept per slide ideally)
===================================================================

1. TWO-TIER SPEND CAP ENFORCEMENT
Each agent has a maximum spend cap. At 90% of the cap, a transaction is allowed but flagged (early warning, visible risk). At 100% of the cap, the transaction is denied outright. This surfaces risk building up before it becomes an actual violation, rather than a single hard cutoff with no warning.

2. SCOPE ENFORCEMENT
Each agent is locked to one allowed transaction category (e.g. a Grocery Agent can only transact in "grocery"). Any attempt outside its category is denied and logged as "off-scope."

3. BURST / RATE-LIMIT DETECTION
If an agent fires transactions abnormally fast in a short window, that pattern alone is caught and denied — even if individual transaction amounts look fine. Protects against a compromised or malfunctioning agent moving fast, not just spending big.

4. GLOBAL KILL SWITCH
One control halts every agent's ability to transact, instantly, fleet-wide. The halt itself is written to the audit log as its own permanent event (not a mutable flag that could be silently changed) — so there's always a record of exactly when and that it was triggered.

5. IMMUTABLE, EXPORTABLE AUDIT TRAIL
Every transaction attempt — regardless of outcome — is permanently logged with a timestamped reason. Exportable as CSV for compliance/regulatory review.

6. POLICY RULES ARE NOT RUNTIME-EDITABLE (deliberate design choice — worth its own slide, this is a differentiator)
Policy rules live in a config file loaded once at startup. There is no API or UI path to change them while the system is running. Framing: "a governance layer that can rewrite its own rules on the fly isn't really governance" — this closes off a real security/tampering risk (insider threat, prompt injection, compromised admin session) that most teams building an editable admin panel would leave open.

7. PROVEN AGENT-AGNOSTICISM (this is the standout technical proof point — give it real visual weight)
Most of the simulated fleet (4 of 5 agents) runs on scripted mock transactions for demo determinism. One agent — the Travel Agent — is genuinely driven by a real local LLM (Qwen2.5:3b via Ollama, running locally, no external API, no cost, no network dependency). It generates its own transaction requests from scenario prompts and submits them through the EXACT SAME evaluation endpoint as every scripted agent, with zero special-case handling in the policy engine.
Result: the LLM has organically attempted off-scope and overspend transactions it was never explicitly scripted to make, and been correctly denied by the same policy engine. When the LLM returns malformed output (bad JSON, markdown-wrapped response, missing field), that's treated as its own governance-relevant failure — denied and logged as "malformed_agent_payload," not silently retried or auto-corrected.
Why this matters: this converts "our system is agent-agnostic" from an architectural claim into something empirically demonstrated with a real, non-deterministic model.

SYSTEM ARCHITECTURE (good candidate for one diagram slide)
===================================================================
Flow: Agent Fleet (mostly simulated, one real local LLM) → Policy Engine → Event Log (Postgres, append-only) → WebSocket broadcast → Dashboard (agent cards, live feed, kill switch, CSV export)

Policy evaluation order inside the Policy Engine (sequential, first deny wins, a flag does not stop evaluation):
kill_switch check → scope_check → spend_cap check → burst_detection

Tech stack:
- Backend: FastAPI (Python), async
- Database: PostgreSQL, append-only event log design
- Real-time: WebSockets, server-push only (no polling/manual refresh)
- Frontend: React (Vite)
- Config: YAML, startup-loaded, not runtime-editable
- Local LLM: Ollama, Qwen2.5:3b, running on local GPU
